# Changelog

## Not yet released

One change reaches what 0.5.0 already did:

- Each reload of the skills also reads `registry-installed.json`, next to your skills folder, and switches off a recipe it marks as revoked. Nothing writes that file yet, so every skill loads as it did.

After updating, restart the daemon with `systemctl --user restart tuxistant`, or log out and back in. The extension is unchanged.

- Browse in Settings, Settings' half: a page beside Skills to find, install, update and remove recipes from the skills registry, close to GNOME's Extension Manager, with a search, categories and their tags, what you installed and the newest, and a page per skill with its risk and reason, its hosts, its versions and, on a click, each action as the model would be given it and the whole recipe. Settings fetches nothing itself, and an install takes the shell's approval card, which the daemon writes. No registry exists yet and none is set, so the page says so and fetches nothing. The daemon's half isn't built yet. Tested in a headless Settings against a stand-in daemon, not yet tried on a real desktop. See "Browsing the skills registry in Settings" in [docs/SKILLS.md](docs/SKILLS.md#browsing-the-skills-registry-in-settings).
- Signing for the skills registry, Tux's side, tested offline and not yet called by anything: `tuxistant/registry.py` checks the index against the registry key that ships with Tuxistant, `revocations.json` against a moderation key the index names, and each recipe against its pinned size and SHA-256, its publisher's signature and Tux's own loader, all with `ssh-keygen -Y verify`. An older index or list of revocations than one already seen is refused, and a state file that can't be read refuses both until it is fixed. Every differing copy of a revocation is in effect until its id is lifted, so one the moderation key signed first can't hide the registry's. The moderation key's copies are kept apart from the index's and never stop an index, and an index that retires the key drops them and its sequence number. The index and `revocations.json` list only the revocations in effect, and the index lists lifts by id, so at the format's limits they fit in what Tux reads, with room left in the index for the skills. Recipes installed from the registry that a revocation covers are switched off with its reason and come back on when it is lifted. It takes the logo fields of the index as the format gives them, but fetches and decodes no image. The registry key shipped now is a placeholder that nothing verifies with. See "Skills from the registry" in SECURITY.md.

## 0.5.0

The stable release, by the owner's choice, and what the website offers. Every change in it was reviewed, and the review's findings were fixed and checked again, but most of what it adds has only run in tests, in an isolated GNOME Shell and in evaluations against a real model, not yet on a real desktop: each entry below says how far it was tried. 0.2.0 is the last release whose additions all worked on the owner's own desktop.

Four changes reach what 0.4.0 already did:

- Cloud sends nothing until you agree to what it sends, even if you had it on. See the first entry below.
- "What's my IP address?" no longer says this computer's Tailscale address until you turn that on, on the This computer skill's page in Settings.
- A Fn hold within 2 minutes of the last one carries on that conversation, where in 0.4.0 each hold started a new one: Tux remembers what was said, and what it read still counts, so a request that ran without a card in 0.4.0 can need one when it comes after a hold that read your mail or files.
- A code skill you added that loaded in 0.4.0 can be refused now, by three rules 0.4.0 didn't have. No action of it may start like a built-in one: the first word of its tool name, up to the first `.` or `_`, with or without an `s` on the end, may not be `app`, `calendar`, `disk`, `file`, `home`, `knowledge`, `light`, `mail`, `media`, `new`, `news`, `phone`, `research`, `shell`, `system`, `task`, `time`, `timer`, `translate`, `weather` or `web`, so `timers_extra.list`, `news_digest.get` and `new_note.add` are refused. The skills you add bring six actions at most between them, where 0.4.0 allowed 32 to each: 0.4.0 kept no note of what had loaded, so at the first start they are counted in the order their folders sort by name, and a skill that would go past six is refused whole, as is any one skill with seven or more, while a later one that still fits loads. And its `skill.yaml` may not use YAML anchors or aliases, `&` and `*`. The new limit of 16 levels deep can't refuse one, as 0.4.0 already held its parameters to 6. A skill refused this way isn't offered to the model, so Tux can no longer do what it did. Settings lists it under "Skills with problems" by its folder name, with the reason, and `tuxistant doctor` and `tuxistant skills reload` print it. Its folder and what it saved are left alone, so renaming the action, taking out the anchors, taking out another skill or, for one with seven or more, taking it down to six or fewer brings it back, with no restart.

After updating, run `./install.sh`, which copies the new extension, then log out and back in, which loads it and restarts the daemon. Until the daemon restarts it keeps sending multi-step requests to Anthropic with the switch and a key alone. Until the extension loads, Tux's question doesn't stay up with "Hold Fn to answer", and dictation says "Dictating…" without saying how to stop.

- Cloud now needs your agreement, and the daemon checks it. Turning Cloud on, on the Multi-step tasks page, shows what leaves this computer, to Anthropic and which model, and when, what never leaves without a click on that item, and a link to Anthropic's privacy policy. Turn On can't be pressed until "I understand and agree" is ticked, and Cancel is the default. The agreement is kept in the config with its date, the provider, the model and the version of what is sent, and the page says "You agreed on" that date, with a Withdraw button that turns Cloud off and forgets it. The daemon uses the cloud only while that agreement covers the current version, provider and model, and checks right before every request it sends, a retry included: the Claude library no longer retries on its own, and Tux tries again once after a lost connection or a server error, checking first. So without an agreement Cloud turned on over D-Bus or in the file sends nothing, a new model asks again, and switching Cloud off, Withdraw or a new model stops a task before its next call, with "Cloud was turned off, so I stopped.", even when it comes while a request is out, in which case the reply isn't read out, and drops a task waiting for your answer. Switching Cloud off keeps the agreement, so while it is kept the switch alone, from Settings or over D-Bus, turns Cloud on again; only Withdraw forgets it. A model name with a line break or more than 100 characters is refused with "That is not a model name", in Settings and over D-Bus, and so is one with a space at either end over D-Bus, as Settings trims the spaces first. **If you had Cloud on before this, it stays at home until you agree:** the page says so, and turning it on asks. **Restart the daemon after updating** (`systemctl --user restart tuxistant`, or log out and back in, as the installer now says): until then the old daemon keeps sending multi-step requests to Anthropic with the switch and a key alone, and can't record an agreement. Settings sees this, says so, shows the switch as the old daemon holds it so you can turn Cloud off, and doesn't offer the agreement. `SetConfig` takes `cloud_consent` to record or withdraw it (see "Cloud agreement" in docs/CONTRACT.md). Tested only in a headless Settings and against a stand-in for the Claude library, not yet tried on a real desktop.
- Every skill in Settings opens to a page of its own, built in, a recipe or a code skill you added: where it comes from, with the file of yours and "Open file" or "Open folder", its permissions in words and the ones that set its risk, and for each action the tool name, description and parameters the model is given, word for word from the code that builds its list. The whole manifest is there, read-only and fixed-width, with a Copy button, as it was loaded. Its keys, values, numbers and comments are in colours that follow light and dark, and keys go bold instead under high contrast. The colours come from the same YAML reader that loads the skill, so they can't show a key as a comment or a string, and past a mistake in the file the text is plain. A built-in skill names the Python module behind its manifest. A skill's settings moved from General to its page, keys, defaults and saving unchanged: General keeps the server, its key, the pipeline, listening, the shortcuts and the instructions. Settings whose skill isn't loaded, such as the TP-Link account when Lights can't run without bubblewrap, are listed apart on the Skills page, so they can still be changed or removed. What a skill says about itself is shown as plain text, never as markup. `SkillDetails` on D-Bus returns it; an older daemon that lacks it still gets a page, with the permissions, the actions by name and the settings. Tested only in a headless session, not yet tried on a real desktop.
- Settings keeps your place when a list changes. When a new request comes into History, or the themes or skills are read again on coming back to the window, the keyboard focus stays on the same entry, or the one now in its place if it went, rather than moving to another row, and the Skills page stays scrolled where it was. Themes and skills that haven't changed aren't rebuilt at all, and closing a skill's page after the list changed goes back to that skill's row. Tested only in a headless session, not yet with a real screen reader.
- "What's my IP address?" no longer says this computer's Tailscale address, and Tux doesn't look for one, unless you turn on "Say my Tailscale address" in Settings, on the This computer skill's page. It starts off, so the address isn't given away on a shared screen, a call or a recording. Tested with a stand-in for `ip` and in a headless Settings, not yet tried on a real desktop.
- Dictation: tapping Fn twice now dictates hands-free until you tap Fn again, where before the second tap's release ended it at once and nothing was typed, while the orb still said "Dictating…". Tapping Fn, then holding it, is push-to-talk as before. The orb says which it is and how to stop: "Dictating… tap Fn to stop", "Dictating… let go of Fn to stop", or with `Ctrl+Super+D`, "Dictating… press Ctrl+Super+D again to stop". A go that types nothing now says so, "That was too short, so nothing was typed." or "I didn't hear any words, so nothing was typed.", rather than vanishing. Tapping twice while Tux is still speaking or closing a reply is hands-free too: the keys are timed as they arrive, not after the reply has stopped, which can take 2 s and made the second tap look like a hold. The talk shortcut, Talk in the menu, a talk hold or something said aloud now ends a go and types what it heard, where before they threw it away without a word. Waking from a suspend ends a hands-free go or one from the shortcut and says "The computer went to sleep, so I stopped dictating and nothing was typed.", where before it went on listening after the lid was opened; a held go still ends and types when the Fn helper lets go on waking. Words or a note for an earlier go no longer take "Dictating… tap Fn to stop" off the screen while the next go listens: a note shows under it, then gives way to it. Once a go stops listening its line goes, where it stayed a few seconds more. A Fn tap followed at once by Fn with another key, while a go from `Ctrl+Super+D` listens, leaves that go alone, where it threw away everything it had heard without a word, and two Fn taps no longer turn it into a hands-free go; and a Fn shortcut on the press that started a go drops only that go, no longer the words of an earlier go that were still being turned into text. A new `DictationMode` D-Bus signal carries the mode; an extension from before it still shows "Dictating…", and hands-free works with it once the daemon is restarted. Tested in an isolated GNOME Shell with the real extension and daemon, and with Fn as the helper reports it; the suspend check only with a stand-in clock, and the slow reply with a stand-in that takes 0.35 s to stop. Not yet tried on a real desktop with a real Fn key or a real suspend.
- Follow-ups: a Fn hold within 2 minutes of the last one, counting time the computer was asleep, carries on the same conversation, so Tux remembers what was just said, and what the conversation has read still counts, so a card it needed is still needed. When Tux asks you something, such as which of two files to print, the blob and the question now stay on screen for about 10 seconds after it speaks, with "Hold Fn to answer", even with "hide on release" on. Your answer on a hold you press while the question is up goes straight to a multi-step task that asked, however long Fn is set to take to count as held; a later hold goes the usual way. A hold that hears nothing puts the question back for the seconds it has left, and words or a note from an earlier dictation go leave it on screen, with the note under it. Waking from a suspend ends the conversation if its 2 minutes went by in the sleep, and takes the question down if its seconds did, rather than showing it again. Only Tux's own question brings up the hint, never a mail or a web answer it reads out that happens to end in a question mark. Stop, a lock, Deny on a card, the talk shortcut or 2 minutes without a hold start a new conversation, but the talk shortcut or a Fn shortcut that only ends a dictation go leaves it alone; starting a go, a timer or reminder going off, or Settings reading out a voice takes the question down, so the hold after it is a new request in the same conversation, while Fn followed at once by a Fn shortcut leaves the question up; Stop, a lock and Deny also forget the files it last found. A new server, key, voice or instructions, or a skill switched on or set up, take effect on the next hold, over a new connection. A kept connection that doesn't answer a ping within 2 seconds, as after a change of network, is replaced before the words go into it, rather than leaving the turn thinking for a minute. Built and tested in an isolated GNOME Shell with a stand-in server, the suspend only with a stand-in clock and the dead connection only with a stand-in that stops reading; not yet tried on a real desktop or against the real server, so whether LocalAI keeps an idle session open for 2 minutes is unknown. The extension changed, so it needs a logout to load.
- Recipe skills: one YAML file in `~/.local/share/tuxistant/skills/`, with no code, that asks a host it names for something and says what came back, opens an app or a Settings page, or says a sentence. Tux writes the card from the request it will send: always for a post, a request with your own words in it, or a device on your local network, and never cut. Nothing a recipe reads reaches the model: Tux says it in the recipe's sentence. A recipe can't reach this computer, its loopback or link-local addresses, its containers and virtual machines, Tailscale's own address, or the servers this install uses, by name and by the addresses their lookups last gave, has no shell, files, clipboard, D-Bus or headers, and a new host waits until the file is taken out and put back. The servers this install uses are looked up each in a thread of its own, alongside the host and inside its 8 seconds, so a slow `homeassistant.local` doesn't add to the host's time, and what a name's lookup last answered is used while its next lookup runs. A failed lookup isn't kept, so a name no lookup has answered yet is looked up for each call and waited for: if that lookup hasn't ended within the 8 seconds, the host "doesn't answer" and nothing is sent. A lookup still running from before the call that then fails is followed by a fresh one, and the request is judged again just before it is sent, after any card, by the servers the settings name then and what they have answered since; after a card, one with no answer is looked up again. It opens only apps in the app grid, and names a Settings page as Settings shows it. The same request again within 5 seconds sends nothing and shows no second card, and Tux says the answer again. Six examples are in `docs/examples/recipes/`, with eleven actions between them. Not yet tried on a real desktop. On the real model, ten repeats, six recipe actions moved the built-in routing cases by about 1.2 points, down as installed and up with Home Assistant only, so the budget stays at six; "Show me the Wi-Fi settings" goes to `work.sound` 9 of 30 as installed: a tighter wording fixed that but lost "Where's my phone?" 20 of 20 with Home Assistant only, so it was not kept. "What's the price of gold?" still gets no tool beside `coins.price`, and goes to web search without it: 11 of 13 wordings left it with no tool, and two of the three that said "only" sent it to web search but lost "What's bitcoin at?" and "How much is one ether in dollars?" (see TESTING.md).
- Skills you add, code skills and recipes together, bring at most six actions, and none may start like a built-in action, judged on the tool name the model sees, plural or not: `file.delete`, `files.delete`, `file_trash.now` and `shell_run.now` are all refused. Skills that were loaded keep their place, after a restart too, so a skill past the six, the one just added, is refused with a reason, though at the first start after 0.4.0, which kept no note of what had loaded, they are all new and counted in the order their folders sort by name. One skill with seven or more actions is refused on its own. A loaded skill you give more actions is counted after the others, so it is the one refused, never another skill that was working. A loaded skill also keeps its id and action names, so a new skill, or an edit to another, that would take one is refused instead, after a restart too. A loaded skill keeps its place whatever it is refused for: until Tuxistant restarts the version it had before stays in use while that is still allowed, and after a restart, or when its file broke while Tuxistant was off, it keeps its place at the size it had, so neither a skill refused before nor another skill's new actions can take that room. Only taking its file or folder out frees it, and renaming it counts as taking it out. Skills can swap actions in one edit each. Tux reads `skills-loaded.json` and `skill-grants.json` only as plain files of at most 1 MB: a damaged `skills-loaded.json` is ignored, and a damaged `skill-grants.json` is left as it is, and until you fix it or take it out no skill you added gets the network or a setting, even one allowed before; taking it out allows every skill of yours what it asks for now. Tux watches `skill-grants.json` and reads it again whenever it changes, so an edit you make to it counts at once, and a second recipe with the same id as one of yours can't change what the first was allowed. When it can't be saved, as on a full disk, the skills already allowed carry on and one not allowed before is refused with a reason that says so, until it can. A code skill that can't run without bubblewrap uses none of the six. A recipe named `.yml` or `.json` is listed as a problem. Settings lists skills that didn't load under "Skills with problems", says "A recipe you added." or "A skill you added." on yours, and has an "Open skills folder" button. `SkillProblems` on D-Bus returns them.
- Recipes can do a desktop action from a short list Tux keeps in its own code: show a notification, turn Do Not Disturb, Night Light or dark style on or off, or lock the screen, as `desktop: {action: night_light, turn: on}`. A recipe names only the entry, never a bus, method or setting, and an unknown entry or field is refused with a reason. Each entry has its own card rule: locking the screen always shows one, Do Not Disturb and Night Light when they turn on (Night Light may not tint the screen until its schedule starts, hours later), and the others none. A repeat within 5 seconds is said again rather than done, but only until the same entry is changed again, so on, off and on again does all three, and two calls to one entry that overlapped, as one left running by a cancelled turn can, keep no answer. A notification's title always names the recipe, and its text is the author's with only choices and numbers in it. The `evening.yaml` example uses four of them. A screenshot isn't one, as GNOME lets only its own tools take one without asking. Not yet tried on a real desktop.
- The `skill.yaml` of a code skill you add is refused when it uses YAML anchors or aliases, as a recipe is, or is nested more than 16 levels deep. 5.5 KB of aliases held the daemon for 8 seconds on every reload, a bigger file for minutes, and 64 KB of `[` for over a minute.
- Research pages are no longer fetched from the Home Assistant server set in Settings, as they already weren't from the voice, translation and search servers, and a server's name is refused in any spelling the resolver reads as it: a page's host has to be an address or a plain name of letters, digits and hyphens once IDNA has encoded it, as the resolver will, so fullwidth letters and a soft hyphen become the server's own name, and a backslash escape, an underscore or a % is refused. So is port 0, which was read as port 80. A server in Settings may have an underscore or a hyphen at either end of a label, as Settings allows. One with something else, such as a backslash, which only an edited `config.json` can hold, stops research and recipes, and Tux says that a server address in Settings has characters it can't check. The servers' addresses are looked up while the search runs and waited for before the pages start their clocks, and what a lookup answers is kept for a minute, so a Home Assistant that takes seconds to answer costs the pages nothing. A failed lookup isn't kept, so one that hasn't answered any lookup, as `homeassistant.local` away from home, is looked up again then and waited for too, still before the pages' clocks, and no page is read if that lookup hasn't ended within research's time. Each page and redirect is checked against the servers the settings name, and what they have answered, after its host's lookup and just before it is opened.
- Research no longer reads a page at this computer's own addresses, public ones too, such as a global IPv6 address from your internet provider or a NAT64 address that leads to its public IPv4, or on the network of one of its containers or virtual machines, whatever range that was given, as recipe requests already didn't. Before, a page was refused only off the open internet or at the install's own servers, so a search result whose name pointed at this computer's public IPv6 could have research read any service listening there, such as a port Docker publishes, and say what it found. This was so in 0.4.0 too.
- A web page cut short, by the 8-second limit or by a server that hangs up before the length it gave, is no longer read as if it were whole, and research leaves it out. A recipe's answer cut short the same way makes Tux say the host didn't answer: before, a price cut to its first digits was said as the price.
- "Send the photo from yesterday to my phone" is a routing case of its own, in every setup. It still goes to the Trash tool, with files older than a day, in three of the four measured setups, and only the Trash card stops it. A `phone.send` wording that named photos sent it to `phone_send`, but with Home Assistant only and no recipes it cost "Where's my phone?", 9 of 10 to 3, so it was not kept. Even at `phone_send` it would not find the photo: it asks for result 1, which after an earlier search is that search's first file (see TESTING.md).
- The routing and flow evaluations no longer read your own skills folder, so their numbers are the same on every computer. `TUX_EVAL_RECIPES=1` adds four of the example recipes, six actions, and their cases, including ones a recipe could take from a built-in tool.

## 0.4.0, a preview

A preview. Nothing new here has been tried on the owner's own desktop yet: opening apps and Settings pages, the facts lookup's card and the Home Assistant matching have run only in tests and in evaluations against a real model.

Two changes reach what 0.3.0 already did:

- The facts lookup, when the voice model picks it, now refuses some questions about the home and asks for a click on others, where 0.3.0 sent whatever it was given to Wikipedia and web search. A fact that shares a word with home questions, such as "How many planets are in our solar system?", now costs a click on those turns.
- Home Assistant reads more of a long name, so a request that reached one device in 0.3.0 can now get "Say which one".

After updating, restart the daemon with `systemctl --user restart tuxistant`, or log out and back in. The extension is unchanged. For only what has been seen working, stay on 0.2.0.

- Tux opens apps and Settings pages: "Open Firefox", "Open Spotify", "Open the Bluetooth settings", "Open the display settings". It opens only what is installed, and asks which one when several match. A shortcut that isn't from an installed package, such as one added in your home folder, shows a card first with the command it runs, and says when it starts over D-Bus, in a terminal or in another folder. One whose command has a field code other than those for files and addresses is left alone, as some, such as `%i` for its icon, are filled in by `gio launch` after the card. "Open Firefox", "Open Spotify" and the Settings pages reach it every time in the measured runs, and "Close Firefox" no longer opens Firefox. Not yet tried on a real desktop.
- Home Assistant finds a device by any whole word in the first 255 characters of its name, not only the first 40. "Garage door" now finds a switch named "Shelly relay channel one outside wall garage door", and the words of "(9 more characters)" no longer find anything. Areas work the same way. What Tux says and the card still show the name cut to 40 characters.
- The facts lookup now refuses questions about the music playing, timers and the home that its word filter knows by their shape, such as "Is the front door locked?", "How much longer is the pasta?" or "Is there a timer set?", on every turn. A question with a word that is often about the home but also used in facts, such as thermostat, timer, countdown, our or locked, in a shape the filter can't tell from a fact, such as "Set the thermostat to 21" or "Who invented the egg timer?", now shows a card first. It says which words would be sent: to Wikipedia, and to your search server if Wikipedia doesn't answer. In a conversation that has already read something private, the usual card for reaching the internet is shown instead. Nothing leaves without a click. In such a conversation, a sum, a question the lookup refuses, or any question while looking things up is turned off now gets no card, as nothing leaves your own server. Before, on a turn from the shortcut or a hold turn not sorted as a fact, the voice model could send either kind to Wikipedia and web search with no click. A private question with none of these words, such as "Who's at the door?", can still go there on those turns. Where the shapes can't tell the two apart, the lookup refuses, so a few facts, such as "Is the Large Hadron Collider still running?" or "Who left on the Mayflower?", are never looked up. Facts that share those words, such as "Who invented the garage door opener?", "How does the heating element in a kettle work?" or "Who sang Sweet Child O' Mine?", get the card and are looked up after the click.
- On an Fn hold, every word 0.3.0 kept from the sorter still keeps a question from it, such as my, our, thermostat, timer, countdown, how much longer, locked or front door, so those questions go the normal way, as in 0.3.0. So do facts with those words, such as "How many planets are in our solar system?" or "Who sang My Way?". Questions that only hold now, with words such as today, tomorrow, latest or currently, and questions about Tux itself, such as "What are your skills?" or "How can you help me?", now go the normal way without being sorted too. So does the colour or brightness of the lamp, light or bulb in the shapes the filter knows, such as "What colour is the lamp?" or "How bright is the lamp?", which the facts lookup refuses as well. Words people start with, such as "Okay." or "Hey Tux", no longer hide the shape of the question after them. A song title right after "who sang", "who sings", "who recorded" or "who performed" is sorted, even in lower case, as in "who sang yesterday". A time after the title, as in "Who sang at the Super Bowl tonight?", or words such as "Okay," before it, keep the question from the sorter.

## 0.3.0, a preview

A preview. Most of what is new here has run only in tests and in evaluations against a real model, not yet on the owner's own desktop. Mail search was asked four times there: two answers, and two turns cut short. Web search, facts, your own skills, media, timers and Home Assistant have not yet been tried by voice on a real desktop, and Home Assistant has never been used with a real home.

Three changes reach what 0.2.0 already did:

- Every Fn hold is now turned into words first, and a separate model call decides whether it is a question of fact, before the voice model hears it. Apart from the four mail questions, which may have gone this way, it has not run on a real desktop.
- Tapo lights, which worked in 0.2.0, now run in the skill sandbox. That needs `bwrap` and `prlimit`, an x86_64 or aarch64 computer, and Linux 6.12 or newer with Landlock on. Lights needed none of this in 0.2.0, so without it they stop working after the update. As a skill with the network, they also now ask for a click when the conversation has already read something private, such as your calendar or a file, which 0.2.0 never did. They have not been tried on a real desktop since the move.
- The daemon now starts at login on every install, not only with the Fn helper. That changes nothing for an install with the Fn helper, and has not been tried without one.

After updating, restart the daemon with `systemctl --user restart tuxistant`, or log out and back in. Until then the old version keeps running. For only what has been seen working, stay on 0.2.0.

How well the model picks the right tool with all of this offered is measured in [docs/TESTING.md](docs/TESTING.md), with what it still gets wrong, such as "Open Spotify" pressing play.

- **Your own skills, with code.** A skill can bring its own program, which runs in a bubblewrap sandbox and may ask for the network and nothing else. Put one in `~/.local/share/tuxistant/skills/` and it loads, changes and goes while Tux runs, with no restart. [docs/SKILLS.md](docs/SKILLS.md#code-skills) shows how to write one. Tapo lights now run this way, and find their bulbs again with a broadcast the first time after updating.
- **Home Assistant.** "Turn off the kitchen light", "Is the front door locked?" and "Set the heating to 21". It controls and reads lights, plugs, fans, heating, blinds, locks, scenes and scripts by the names they have in Home Assistant. Unlocking, opening, activating a scene and running a script show a card first. Add the address and a long-lived access token in Settings. Until both are set the model isn't offered it, so nothing changes for anyone without one. The token is never handed back, and a new address clears it.
- **Timers and reminders.** "Set a pasta timer for 8 minutes", "Remind me at 5pm to call mum" and "How long is left on the pasta?". Tux says it out loud when it is due and leaves a notification, and they are kept through a restart. On a locked screen there is only the notification, and the words come if you unlock within an hour for a timer, or a day for a reminder. After that only the notification remains. "Chime for timers" in Settings, which starts off, adds a short sound. The daemon now starts at login on every install, with or without the Fn helper, as a reminder can't be said if nothing is running.
- **Media.** "Pause the music", "Skip this song", "What's playing?", "Turn it up" and "Volume 40". It reaches players through MPRIS, which Spotify, VLC and browsers speak, though so far it has only driven stand-in players. The volume never goes above 100 percent.
- **Mail search.** "When did I book the flights?" or "What did my landlord say about the rent?" is answered from the mail Thunderbird keeps on this computer, with who sent it and when. It is off until you turn on "Search my mail" in Settings. Mail goes nowhere but your own server. Junk and Trash are skipped, by Thunderbird's own mark or by their name. Sign-in codes and passwords are hidden by the words around them and their shape, and [docs/ROADMAP.md](docs/ROADMAP.md) lists what gets past both. An answer from a sender who is new to you comes with a warning.
- **Facts from what's written down.** A question of general knowledge asked on an Fn hold is answered from Wikipedia, then from web search, with no click. Tux says it doesn't know when neither clearly answers, instead of guessing. It repeats what a page says, even when the page is wrong, and in the last facts evaluation one of 54 hard questions got a wrong answer. Sums are worked out on this computer. "Look up facts on Wikipedia" in Settings, which starts on, turns the lookup off.
- **Web search and research.** "Search the web for flights to Lisbon" reads out the top results, and "Research electric bikes" reads a few pages and tells you what they say, naming its sources. Both need a SearXNG server of your own with JSON output turned on, which Settings can point at.

### Fixed

Most of these fix code that is new in 0.3.0. They were found in tests and review before this release, not in use. Only the entries on lights, the calendar messages in Settings, and the key that the evaluations, the voice check and the demo video send change what 0.2.0 did.

- A timer or reminder whose words couldn't be spoken, for example with the speech server down, is no longer marked missed at once. It stays pending and is tried again after one, two and four minutes, and only then counts as missed. The error shows once for each try. Once some of the words were heard it counts as said, so it is never said twice.
- The timer chime plays to its end however the words fail, such as a refused connection or a timeout, not only on a server error. A key press still cuts it.
- A timer or reminder whose words were cut by the screen locking before any was heard is no longer recorded as said. It is said after the unlock, late if it has to be.
- One timer waiting to be tried again after its words failed no longer holds back the ones due after it. They are said on time.
- If the timer scheduler ever fails, it is logged and starts again, so timers keep working for the rest of the session.
- In the daemon as built, the timer chime would never have played on a locked screen, and a timer that came due while the screen was unlocked would have been marked missed instead of said. A setting was read by a name that was lost when the daemon's start-up code was split in two. A test caught it before any timer ran in use.
- If the screen-lock check fails while it is being set up, speech stays locked, so a timer shows a notification and is not said aloud on what may be a locked screen.
- A damaged `timers.json` holding an absurd id or time loses only that row. A due time in the last days of the year 9999 no longer stops every timer listing.
- A saved id counter at its very top no longer hands out ids that the next start drops.
- Lights are offered to the model only once a TP-Link email and password are in Settings.
- A Home Assistant switch or helper whose name or id says alarm, siren, lock, security, arm, disarm or deadbolt, or a garage, door or gate that isn't also a light, lamp, bulb, heater or fan, now waits for a click whichever way it is switched. The name and the id are judged apart, and joined spellings such as Doorlock, Frontdoor and Garageopener count. A long name is judged past the 40 characters the card shows, and a card is shown if either the shown or the longer name says so.
- Questions about the music playing, timers and the home that use words such as my, our, this song, timer, time left, locked, front door or the heating, like "How much time is left?", "Is the kettle on?" or the temperature in the kitchen, now go the normal way without being sorted, so the sorter doesn't send them to Wikipedia, though in this release the voice model can still pick its lookup for one, which sends it there. The release after this one fixes that. One worded without any of these, such as "Who's at the door?", still depends on the sorter: in the last measured run it called "What colour is the lamp?" a fact once, which sends the question to Wikipedia.
- Without Evolution Data Server's Python bindings, Settings now names the packages to install, evolution-data-server and gir1.2-ecal-2.0, in the same words the voice uses, instead of suggesting an Online Account.
- Settings no longer tells you to add an Online Account when it can't list your calendars, for example after a timeout or with a daemon that hasn't restarted since an update. It says the listing failed instead.
- The evaluations and the live protocol test send the key only to a server named for the run, or to one saved in Settings that is neither the default nor on this computer. They share one set of stand-ins, which now also blocks timer notifications and never starts a code skill's process.
- The voice check and the demo video now check the server before they send the key, like the evaluations. A demo video with no server the key may go to comes out silent. A server on this computer is refused unless it is named for the run: a loopback address in any spelling, such as 127.1, 2130706433 or ::ffff:127.0.0.1, a localhost name such as ip6-localhost, the machine's own name, and any address its network interfaces hold. Nothing is looked up, so another name that `/etc/hosts` gives this computer is not caught. The end-to-end harness now needs `TUXISTANT_SERVER` as well.
- Text from a code skill can no longer carry chat-template delimiters to the model. An answer or an error loses its `<` and `>`, and a skill whose name, description, version, action description or params text holds them is refused with a reason.
- `./uninstall.sh --purge` now also removes `~/.local/state/tuxistant`, where code skills keep what they save in `/state`, such as the addresses of the bulbs the lights found. Without `--purge` it is kept, and the uninstaller says so.
- A new test, `tests/test_names.py`, fails the suite on any name a function reads as a global that nothing defines. It reads every file under `tuxistant/` and `tools/` without running them, so it would have caught the timer chime bug above.

## 0.1.0, a preview

The first tagged release. It is a preview: everything here is built and tested, but some of it has only run in tests and in an isolated GNOME Shell, not yet on a desktop in daily use. [docs/ROADMAP.md](docs/ROADMAP.md) says which parts those are, under "Where things stand".

It needs GNOME Shell 50 on Wayland, Python 3.14, and a LocalAI server of your own with an 8 GB NVIDIA GPU. [README.md](README.md) has the full list and the install steps, and [server/](server/README.md) sets up the server.

What it does:

- **Talk and listen.** Press `Ctrl+Super+Space` or hold Fn, ask, and Tux answers out loud. A blob on screen reacts while captions show what was heard and said. Speech, the model and the voice all run on your own server.
- **Dictation.** Tap Fn, then hold it and speak, and your words are typed where the cursor is. It never presses Enter.
- **Skills.** Weather and news, finding and opening files, sending a file to your phone or ringing it, moving old files to the Trash, Tapo smart lights, translation spoken in a native voice, facts about this computer, and shell commands.
- **Approval cards.** Anything that changes something or sends a file off the computer shows exactly what will happen and waits for a click. Read-only commands run in a sandbox without one.
- **Several steps in one request**, on your own server, or with Claude if you turn on Cloud and add your own key. Cloud is off by default.
- **Four themes**, and you can write your own as a JSON file and a shader.
- **A Settings app** for the server, voice, look, skills and history, and `tuxistant doctor` to check an install.
- **A server kit** in `server/`: one script that installs LocalAI, the models and the voices, then tests them.

Known limits are listed in [docs/ROADMAP.md](docs/ROADMAP.md), and what the security reviews found and didn't cover is in [docs/SECURITY.md](docs/SECURITY.md).
